Inversion of Control (IoC) in Spring Boot — The Complete Picture
1. The Core Idea (Simplest Explanation)
Normal way of writing code: Your objects create their own dependencies.
java
class Car {
    Engine engine = new Engine(); // Car controls creation of Engine
}
With IoC: You don't create the dependency yourself — you let something else (a "container") hand it to you.
java
class Car {
    Engine engine;
    Car(Engine engine) {  // Someone else gives me the Engine
        this.engine = engine;
    }
}
That's it. That's the whole concept. "Inversion of Control" means: control over object creation and wiring is inverted — taken away from your class and given to a framework/container.
Think of it like a restaurant. You (the class) don't cook your own food (dependency); you just place an order, and the kitchen (Spring's IoC Container) prepares and serves it to you.
________________________________________
2. Why Does This Matter?
Without IoC:
•	Classes are tightly coupled (Car is glued to a specific Engine implementation).
•	Hard to test (can't swap in a fake/mock Engine easily).
•	Hard to change behavior without editing code everywhere.
With IoC:
•	Loose coupling — Car just needs an Engine, doesn't care which one.
•	Easy to test — inject a mock Engine in unit tests.
•	Easy to swap implementations (e.g., PetrolEngine → ElectricEngine) without touching Car.
________________________________________
3. How Spring Implements IoC: Dependency Injection (DI)
IoC is the principle. Dependency Injection (DI) is how Spring actually does it.
Spring has a container called the ApplicationContext (the "kitchen"). It:
1.	Scans your code for classes marked as "manageable" (beans).
2.	Creates instances of them.
3.	Figures out what each one needs (dependencies).
4.	Injects those dependencies automatically.
5.	Manages their entire lifecycle (creation → use → destruction).
The Building Blocks
Concept	What it means
Bean	An object managed by Spring's container
ApplicationContext	The IoC container itself — holds and manages all beans
@Component / @Service / @Repository / @Controller	Tell Spring "manage this class as a bean"
@Autowired	Tell Spring "inject a dependency here"
@Configuration + @Bean	Manually define how to create a bean
________________________________________
4. Real World Example
Imagine an e-commerce app: an OrderService needs a PaymentService to process payments.
Without IoC (tightly coupled — bad practice)
java
class OrderService {
    private PaymentService paymentService = new StripePaymentService(); // hardcoded!

    void placeOrder() {
        paymentService.pay();
    }
}
Problem: If you want to switch to PayPal, or mock payments in a test, you must edit OrderService.
With IoC / DI (Spring way — good practice)
java
interface PaymentService {
    void pay();
}

@Service
class StripePaymentService implements PaymentService {
    public void pay() { System.out.println("Paid via Stripe"); }
}

@Service
class OrderService {
    private final PaymentService paymentService;

    // Constructor Injection — Spring automatically provides the implementation
    @Autowired
    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    void placeOrder() {
        paymentService.pay();
    }
}
Now:
•	Spring's IoC container scans, sees @Service on both classes.
•	It creates a StripePaymentService bean.
•	When creating OrderService, it sees the constructor needs a PaymentService, and injects the StripePaymentService bean automatically.
•	You never wrote new StripePaymentService() anywhere — Spring did it for you.
Switching providers (e.g., to PayPal) later means just creating a PayPalPaymentService implements PaymentService and marking it @Primary, or using @Qualifier — zero changes to OrderService.
________________________________________
5. Types of Dependency Injection in Spring
Type	Example	Recommended?
Constructor Injection	public OrderService(PaymentService p)	✅ Best practice
Setter Injection	@Autowired public void setPaymentService(...)	⚠️ Use for optional deps
Field Injection	@Autowired private PaymentService paymentService;	❌ Avoid in production code
________________________________________
6. Best Practices
1.	Prefer Constructor Injection over Field Injection 
o	Makes dependencies explicit and mandatory.
o	Enables making fields final (immutability).
o	Much easier to unit test (just call the constructor with mocks — no need for Spring or reflection tricks).
2.	Program to interfaces, not implementations 
o	Depend on PaymentService (interface), not StripePaymentService (concrete class). This is what makes swapping implementations painless.
3.	Keep beans stateless where possible 
o	Beans are singletons by default (one instance shared app-wide). Avoid storing per-request mutable state in them.
4.	Use @Qualifier when multiple implementations exist
java
   @Autowired
   public OrderService(@Qualifier("paypalPaymentService") PaymentService paymentService) { ... }
5.	Avoid new for anything that should be a managed bean 
o	If you find yourself writing new SomeService() inside another Spring-managed class, that's a red flag — you're bypassing IoC.
6.	Use @Configuration + @Bean for third-party classes 
o	You can't annotate a library's class with @Component, so wire it manually:
java
   @Configuration
   class AppConfig {
       @Bean
       public RestTemplate restTemplate() {
           return new RestTemplate();
       }
   }
7.	Avoid circular dependencies 
o	If A needs B and B needs A, redesign — this usually signals bad separation of concerns.
8.	Don't overuse @Autowired on setters/fields "just because it's shorter" — it hides dependencies and makes testing harder.
________________________________________
7. Quick Mental Model to Remember
You don't call Spring, Spring calls you.
You just declare what you need (via constructor parameters), and the IoC container figures out how to get it to you and when.
That inversion — from "I build my own dependencies" to "the framework builds and hands them to me" — is the entire essence of IoC in Spring Boot.
@Autowired in Spring Boot — Part 6: Bean Scopes & The Singleton-Prototype Trap
This part covers a subtle bug that catches out even experienced developers.
________________________________________
1. Bean Scopes — Quick Overview
Scope	Meaning	Default?
singleton	ONE instance per Spring container, shared everywhere	✅ Yes (default)
prototype	A NEW instance every time it's requested	❌ No
request	One instance per HTTP request (web apps only)	❌ No
session	One instance per HTTP session (web apps only)	❌ No
java
@Service
@Scope("prototype")
class ReportGenerator {
    // A new instance every time Spring creates one
}
By default, everything you write with @Service, @Component, etc. is a singleton — created once at startup, and that exact same object is reused everywhere it's injected.
________________________________________
2. The Trap: Injecting Prototype Into Singleton
Here's the setup that looks correct but silently fails to behave as expected:
java
@Service
@Scope("prototype")
class ReportGenerator {
    private int reportId;
    public void setReportId(int id) { this.reportId = id; }
    public void generate() { System.out.println("Generating report #" + reportId); }
}

@Service // singleton by default!
class ReportService {

    @Autowired
    private ReportGenerator reportGenerator; // injected ONCE, at ReportService creation time

    void createReport(int id) {
        reportGenerator.setReportId(id);
        reportGenerator.generate();
    }
}
What people expect:
Every time createReport() is called, a fresh ReportGenerator gets created (since it's prototype-scoped).
What actually happens:
ReportGenerator is injected into ReportService exactly once — when ReportService (a singleton) is created at app startup. After that, Spring never touches it again. It behaves like a singleton in practice, defeating the entire purpose of marking it prototype.
java
reportService.createReport(1); // "Generating report #1"
reportService.createReport(2); // "Generating report #2" — SAME object, just mutated!
If two threads call createReport() concurrently, they're mutating the same shared object — a nasty concurrency bug hiding behind what looked like safe prototype scoping.
________________________________________
3. How to Actually Fix This
Option A: ObjectProvider<T> (recommended, modern Spring way)
java
@Service
class ReportService {

    private final ObjectProvider<ReportGenerator> reportGeneratorProvider;

    @Autowired
    public ReportService(ObjectProvider<ReportGenerator> reportGeneratorProvider) {
        this.reportGeneratorProvider = reportGeneratorProvider;
    }

    void createReport(int id) {
        ReportGenerator generator = reportGeneratorProvider.getObject(); // FRESH instance every call
        generator.setReportId(id);
        generator.generate();
    }
}
ObjectProvider acts like a "factory handle" — every call to .getObject() asks Spring for a brand-new instance, respecting the prototype scope correctly.
Option B: @Lookup method injection (older style)
java
@Service
abstract class ReportService {

    void createReport(int id) {
        ReportGenerator generator = createReportGenerator(); // fresh each time
        generator.setReportId(id);
        generator.generate();
    }

    @Lookup
    protected abstract ReportGenerator createReportGenerator(); // Spring implements this at runtime
}
Spring generates a subclass at runtime that overrides this method to fetch a new prototype bean each call. Works, but feels "magic" and is less common in modern codebases.
Option C: Scoped Proxy
java
@Service
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
class ReportGenerator { ... }
This makes Spring inject a proxy instead of a real instance. Every method call on the proxy transparently fetches a fresh real instance behind the scenes. Convenient, but adds a layer of indirection that can confuse debugging (stack traces show proxy classes).
________________________________________
Golden Rule
A singleton bean injected with @Autowired gets its dependency wired exactly once, at creation time — regardless of that dependency's own scope. If you need a "scope-aware" fresh instance on every use, @Autowired a plain field/constructor reference is the wrong tool. Use ObjectProvider<T> instead.

@Autowired in Spring Boot — Part 7 (Final): Initialization Order & The Complete Cheat Sheet
This closes the loop — what happens after injection, and how to make sure things run in the right order.
________________________________________
1. The Problem: "Injected" ≠ "Ready to Use"
@Autowired guarantees a dependency is wired (the reference is set). It does not guarantee that dependency has finished its own setup logic (e.g., loading config, opening a connection, warming a cache).
java
@Service
class CacheService {
    private Map<String, String> cache;

    @Autowired
    private ConfigLoader configLoader;

    // Is cache ready immediately after construction? Not necessarily what you'd assume.
    void init() {
        cache = configLoader.loadInitialData();
    }
}
If init() isn't called automatically, cache stays null until someone remembers to call it manually — a classic bug.
________________________________________
2. @PostConstruct — Run Code Right After Injection Completes
java
@Service
class CacheService {
    private Map<String, String> cache;

    @Autowired
    private ConfigLoader configLoader;

    @PostConstruct // runs automatically, right after all @Autowired fields are set
    void init() {
        cache = configLoader.loadInitialData();
        System.out.println("Cache warmed with " + cache.size() + " entries");
    }
}
Order of operations for any bean:
1.	Constructor runs.
2.	@Autowired fields/setters are populated.
3.	@PostConstruct method runs.
4.	Bean is now considered fully ready and usable.
This is the standard, idiomatic place to put "setup logic that needs dependencies already injected."
________________________________________
3. @DependsOn — Force Bean Creation Order
Sometimes there's no direct @Autowired link between two beans, but one still must be created before another (e.g., Bean B reads a static file that Bean A writes during its setup).
java
@Service
@DependsOn("fileWriterService") // ensures fileWriterService bean is fully created FIRST
class FileReaderService {
    // ...
}
Use this sparingly — it's usually a sign of hidden coupling. Prefer explicit @Autowired dependencies wherever possible since @DependsOn order isn't visible in the constructor signature.
________________________________________
4. ApplicationListener / @EventListener — React After the ENTIRE App Is Ready
Sometimes you need to wait until all beans across the whole app are created — not just your own dependencies.
java
@Component
class StartupTasks {

    @EventListener(ApplicationReadyEvent.class)
    void onStartup() {
        System.out.println("Entire application context is fully loaded and ready!");
        // safe to call ANY bean here, guaranteed fully initialized
    }
}
When to use which:
Tool	Use when...
@PostConstruct	You need setup logic using only this bean's own dependencies
@DependsOn	Bean creation order matters but there's no direct injection link
ApplicationReadyEvent	You need to wait for the entire application context to finish loading
________________________________________
5. THE COMPLETE CHEAT SHEET (All 7 Parts)
Part 1 — Basics: @Autowired tells Spring "find a bean of this type and inject it." Spring scans @Component/@Service/@Repository/@Controller classes and wires them via the ApplicationContext.
Part 2 — Bean Matching: By type → @Qualifier → @Primary → name match → error. Multiple implementations without disambiguation = NoUniqueBeanDefinitionException.
Part 3 — Injection Styles: Constructor Injection (✅ preferred — immutable, explicit, testable, fails fast) > Setter Injection (only for optional deps) > Field Injection (❌ avoid in production).
Part 4 — Collections: Inject List<T> or Map<String,T> to get ALL implementations of an interface — powers the Strategy Pattern cleanly. Use Optional<T> for safe optional dependencies. @Order controls list ordering.
Part 5 — @Bean Methods & Circular Deps: @Bean method parameters are auto-wired without needing @Autowired. Circular dependencies (BeanCurrentlyInCreationException) are a design smell — fix by extracting a coordinator class; @Lazy/setter injection are workarounds, not real fixes.
Part 6 — Scopes: Default scope is singleton. Injecting a prototype bean into a singleton via plain @Autowired silently gives you a "frozen" single instance — use ObjectProvider<T> to get a genuinely fresh instance on each use.
Part 7 — Initialization Order: @Autowired only guarantees wiring, not full readiness. Use @PostConstruct for per-bean setup logic, @DependsOn for explicit creation-order control, and ApplicationReadyEvent for logic that needs the whole app context ready.
________________________________________
The One-Sentence Summary of Everything
@Autowired is Spring's way of saying "don't build your own dependencies — declare what you need (preferably via constructor), and let the container find, create, order, and hand them to you," and almost every real-world gotcha comes from forgetting that the container controls the lifecycle, not just the wiring.
